# Agent B：地點資料與步行路線服務

本工作以 [共用規格](00-product-and-contract.md) 為準。目標是向所有客戶端提供一致的地點搜尋與步行路線。此次先交付規格，收到實作任務後才開始寫程式。

## 工作範圍

1. 提供共用規格所列的 config、places 與 routes API。
2. 匯入首個服務區域的 OSM 酒吧與 pub，保留來源、資料日期與原始識別碼。相同來源 ID 重複匯入不產生重複資料，更新時處理已移除的店家。
3. 依 bbox 與可選店名提供穩定分頁搜尋，支援繁體中文及英文店名。不依賴一般地址地理編碼服務。
4. 部署或接上可配置的 Valhalla，使用 pedestrian 模式，將輸出轉為公尺、秒與 GeoJSON。
5. 檢查站點數、座標、服務範圍、ID 唯一性、終點模式與停留時間，回傳統一錯誤。
6. 計算路網配對距離並執行 100 公尺上限，保留配對點供介面顯示。
7. 提供資料日期、圖磚 style 設定、attribution 與上游服務設定。正式環境使用 HTTPS，伺服器密鑰不進入客戶端設定。

## API 與資料品質規則

- placeId 只用於識別來源；路由依請求內的座標計算，因此已儲存路線的店家即使下架，使用者仍能重新規劃。
- 開放時間保持原始文字，不承諾營業狀態。缺失欄位按契約回傳 null。
- 每段距離與時間以引擎結果為準，不用直線距離除速度冒充路由。
- 引擎無法配對或任一段失敗時回傳 NO_WALKABLE_ROUTE。不得回退至 driving。
- 行程順序完全遵守請求，不自動重新排序，不呼叫最佳化服務。
- 同座標零距離 leg 由服務層正規化，保持 N+1 個 legs 的契約。
- 日誌記錄請求識別碼、錯誤碼、耗時與上游狀態。預設不記錄完整座標、路線內容或使用者位置。
- 設定上游逾時及請求流量限制，說明限制值。429 回傳 Retry-After；Web 客戶端需要時配置明確的 CORS 允許來源。

## 第一批交付物

Agent B 先提供 API 契約文件、固定測試資料與完整請求回應範例，讓 Agent A 能平行開發。範例至少包含單程成功、回到起點成功、空搜尋、不可達及上游逾時。範例中的座標須與實際服務範圍一致，示意路線不得標成真實計算結果。

最終交付包含服務實作、可重現的區域資料匯入及啟動方式、環境變數說明、資料與第三方授權清單，以及 API 驗收記錄。路由引擎與資料需固定版本或日期，公開 demo endpoint 不得成為正式環境唯一依賴。

Agent B 修改服務端、資料匯入、服務端測試與 API 文件，不修改客戶端畫面。新增或變更欄位前，先更新共用規格及範例並通知 Agent A。

## 驗收案例

- 同一資料檔匯入兩次，搜尋結果沒有重複來源 ID。
- bbox 內的酒吧可用店名找到，bbox 外的店不出現在結果中；分頁沒有重複或遺漏。
- 三間酒吧的單程及回到起點，皆產生四個 legs，順序與 waypointId 一致。
- 總距離等於各段總和，總時間包含各站停留時間，未含任何飲酒後跑速假設。
- 相鄰兩點同座標時回傳零距離 leg，後續站點仍正常計算。
- 錯誤座標、九間酒吧、重複 ID、非法 dwellMinutes 與終點模式不符，皆回傳 400。
- 區域外站點回傳 422；超過配對上限或無步行連通路段回傳 422 並提供問題 waypointIds。
- 上游斷線及逾時分別轉為 503 與 504，不洩漏內部服務位址。
- 使用已知繞行路段實際呼叫 Valhalla，確認道路幾何、單位、GeoJSON 經緯順序及步行模式。不能只以 mock 通過此項。
